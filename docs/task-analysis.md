# Разбор задачи «Список задач»

## Цель и результат

Создать аккуратный веб-сайт для добавления задач, отметки выполнения и удаления. Задачи должны сохраняться после обновления страницы. На выполнение отведены два рабочих дня.

Обязательный результат — GitHub-репозиторий с кодом и краткое описание использованных AI-инструментов. Ссылка на работающий сайт даёт преимущество; развёртывание желательно включить в план.

## Согласованные ограничения

- Backend: Java, Spring Boot, ORM и миграции схемы БД.
- Frontend-стек будет выбран позже.
- Аутентификация через Google или email; у каждого пользователя свой список задач.
- Принципы: SOLID, слоистая архитектура http / service / repo и production design в масштабе небольшого приложения.

## Предлагаемая реализация

Один Spring Boot сервис с REST API и реляционной БД. Зафиксированные технологии: JPA / Hibernate через EntityManager, Flyway для миграций, PostgreSQL для хранения. Конкретные версии указаны в AGENTS.md.

Данные хранятся на сервере в БД. Сохранение после обновления не должно зависеть только от состояния frontend или localStorage. При развёртывании базе требуется постоянное хранилище.

Предлагаемая структура области `tasks`:

```text
tasks/
  http/        # REST-контроллеры, request/response DTO, обработка ошибок
  service/     # бизнес-правила, сценарии и транзакции
  repo/        # интерфейс TaskRepository + JpaTaskRepository с EntityManager
    entity/    # JPA entities
    exception/ # именованные ошибки хранения
```

Сервисы работают с JPA entities напрямую; HTTP использует отдельные DTO. Отдельные domain-модели и слой портов не вводятся. Сервисы зависят от интерфейсов репозиториев; каждый интерфейс имеет одну Jpa-реализацию с EntityManager. Транзакции составных сценариев задаются в service-слое. Направление зависимостей: http → service → repo. Для такой задачи достаточно одного приложения; отдельные сервисы, брокер и CQRS не требуются.

## Модель и правила

Предлагаемые поля задачи: `id` (UUID), `userId` (внешний ключ владельца), `title`, `completed`, `createdAt`, `updatedAt`. Даты хранятся в UTC. Владельца сервер определяет из текущей сессии, а не из тела запроса.

- Новая задача создаётся невыполненной.
- Заголовок очищается от пробелов по краям, должен содержать от 1 до 200 символов.
- Одинаковые заголовки разрешены.
- Выполнение можно включить и отменить; клиент отправляет целевое значение `completed`.
- Удаление окончательное; удалённая задача не появляется после обновления.
- Список возвращается в стабильном порядке: новые задачи первыми, при одинаковом времени — по `id`.

Ограничения длины и порядок списка — рабочие предложения для MVP, а не требования исходного задания.

## Предлагаемый API

Подробный проектный контракт: [`openapi.yaml`](openapi.yaml), OpenAPI 3.1.0, версия API `0.1.0`. Это контракт будущего HTTP API; слой хранения уже реализован отдельно. Для email контракт использует пароль; если будет выбран код или magic link, сначала обновить спецификацию. Все даты — UTC, JSON-запросы не допускают неизвестных полей. Ответы с пользовательскими данными и токенами передаются с `Cache-Control: no-store`.

| Метод | Путь | Назначение | Успешный ответ |
| --- | --- | --- | --- |
| GET | `/api/tasks` | Получить задачи | `200`, массив задач |
| POST | `/api/tasks` | Создать задачу: `{ "title": "..." }` | `201`, созданная задача и `Location` |
| GET | `/api/tasks/{id}` | Получить свою задачу | `200`, задача |
| PATCH | `/api/tasks/{id}` | Задать выполнение: `{ "completed": true }` | `200`, обновлённая задача |
| DELETE | `/api/tasks/{id}` | Удалить задачу | `204` |

Все `/api/tasks` требуют входа: без сессии API отвечает `401`. Список содержит только задачи текущего пользователя; изменение и удаление ищут задачу по паре `id` + `userId`. Чужая и отсутствующая задача дают одинаковый `404`.

Ошибочные данные дают `400`, отсутствие сессии — `401`, неверный CSRF-токен — `403`, неизвестный/чужой идентификатор — `404`, превышение лимита — `429` с `Retry-After`, непредвиденная ошибка — `500` без внутренних деталей. При неверном CSRF изменяющий запрос может получить `403` до проверки входа. Ошибки — `application/problem+json` с полями `type`, `title`, `status`, `code`, необязательными `detail`, `instance`, `errors`. Frontend ориентируется на `code`, не на текст сообщения. API не перенаправляет на HTML-страницу входа. Успех показывается после ответа сервера; при ошибке пользователь видит сообщение и может повторить действие.

## Аутентификация и личные данные

Предлагается Spring Security: Google через OpenID Connect (Authorization Code flow), email — регистрация и вход с паролем. Этот вариант зафиксирован в проектном контракте; альтернативу по одноразовому коду или ссылке можно выбрать отдельно до реализации.

- Google: запрашивать только `openid`, `email`, `profile`; идентифицировать внешний аккаунт по `issuer` + `subject`, а не по email. OAuth client ID, secret и разрешённые callback URL задаются для каждого окружения.
- Email: подтверждение адреса одноразовой ссылкой до доступа к задачам, вход и восстановление пароля. Отправка писем через выделенный почтовый компонент, вызываемый сервисом; для разработки — локальный перехватчик писем.
- Пароли хранить только как адаптивные salted hashes через Spring Security PasswordEncoder. Одноразовые токены подтверждения и сброса хранить в виде хешей, с ограниченным сроком и атомарным погашением. Сброс пароля отзывает активные сессии.
- Для браузера использовать серверную сессию и cookie `HttpOnly`, `Secure` в production, `SameSite=Lax`; обеспечить CSRF-защиту изменяющих запросов, смену ID сессии при входе и инвалидирование при выходе. Предпочтительно обслуживать сайт и API с одного origin.
- Ограничить частоту входа, регистрации и отправки писем; ответы восстановления не должны раскрывать наличие аккаунта. Пароли, коды, cookie и OAuth-токены не логировать.
- Совпадение email не объединяет Google-аккаунт с локальным автоматически. В MVP привязка способов входа не предусмотрена; Google-конфликт завершается общей ошибкой входа, email-регистрация возвращает обычный нейтральный ответ. Не раскрывать исходный способ входа, не создавать второй аккаунт и не менять пароль существующего.

Предлагаемые таблицы: `users` (UUID, нормализованный уникальный email, статус подтверждения, даты), `password_credentials` (user ID, password hash), `external_identities` (user ID, issuer, subject с уникальностью пары), `email_tokens` (user ID, назначение, hash, срок, время погашения), `tasks` с обязательным FK владельца. Google-пользователю локальный пароль не создаётся.

### Сценарии регистрации и входа

1. При открытии приложения frontend получает `GET /api/auth/csrf`, сохраняет cookie и токен в памяти. Каждый POST/PATCH/DELETE отправляет `X-CSRF-TOKEN` вместе с cookie, в том числе до входа. После входа, выхода, сброса пароля или истечения сессии получить свежий токен. Затем `GET /api/auth/me` определяет, показывать список задач или экран входа.
2. Регистрация: email + пароль → `POST /api/auth/register` → `202` с нейтральным сообщением. Новый пользователь имеет статус неподтверждённого. Для уже занятого email ответ тот же, существующие данные не меняются. Доступ к задачам и сессия входа не выдаются.
3. Подтверждение: ссылка из письма открывает страницу frontend; токен отправляется в теле `POST /api/auth/verify-email` → `204`. Токен живёт 24 часа и используется один раз. GET-запрос ссылки сам по себе не подтверждает адрес. После подтверждения пользователь входит с паролем.
4. Повторное подтверждение: `POST /api/auth/resend-verification` → `202` независимо от наличия аккаунта. Письмо отправляется только неподтверждённому локальному пользователю; новый токен отзывает прежние.
5. Вход: `POST /api/auth/login` → `200` с профилем и cookie новой сессии. Неверные данные дают общий `401`; только при верном пароле неподтверждённого аккаунта возвращать `403 email_not_verified`. После входа обновить CSRF и загрузить личные задачи.
6. Google: браузер переходит на `/oauth2/authorization/google`; Spring Security обрабатывает callback `/login/oauth2/code/google`, проверяет state и ID token. При первом успешном входе создаются пользователь и внешняя identity; требуется подтверждённый Google email. Успех — редирект на `/`, ошибка/отказ/конфликт — `/login?error=oauth_failed`. После успеха обновить CSRF. Произвольные URL перенаправления не принимать.
7. Выход: `POST /api/auth/logout` → `204`, текущая сессия инвалидируется, cookie удаляется. Данные задач остаются в БД. Другие сессии не завершаются.
8. Восстановление: `POST /api/auth/forgot-password` → нейтральный `202`. Письмо получает только подтверждённый пользователь с локальным паролем. Токен живёт 30 минут; новый запрос отзывает прежние токены сброса. `POST /api/auth/reset-password` с токеном и новым паролем → `204`; токен погашается атомарно, все сессии этого пользователя отзываются. Автоматического входа нет. Для аккаунта только Google пароль этим способом не создаётся.

Email ограничен 254 символами; пробелы по краям удаляются, адрес приводится к нижнему регистру. Не применять специфичные для Gmail преобразования точек и `+suffix`. Новый пароль — 12–128 символов Unicode без обрезки пробелов, нормализации или усечения. При входе допускаются 1–128 символов, чтобы проверка нового пароля не подменяла проверку credentials. Неверный, просроченный или использованный email-токен даёт `400 invalid_token`.

### Маршруты аутентификации

| Метод | Путь | Назначение | Успех |
| --- | --- | --- | --- |
| GET | `/api/auth/csrf` | Получить токен и имя заголовка; при необходимости создать анонимную сессию | `200` |
| POST | `/api/auth/register` | Регистрация email + пароль | `202` |
| POST | `/api/auth/verify-email` | Подтвердить адрес | `204` |
| POST | `/api/auth/resend-verification` | Повторить письмо | `202` |
| POST | `/api/auth/login` | Вход email + пароль | `200`, профиль и session cookie |
| GET | `/api/auth/me` | Текущий пользователь | `200`, профиль |
| POST | `/api/auth/logout` | Выход из текущей сессии | `204` |
| POST | `/api/auth/forgot-password` | Запросить сброс пароля | `202` |
| POST | `/api/auth/reset-password` | Установить пароль по токену | `204` |
| GET | `/oauth2/authorization/google` | Начать Google flow | `302` |
| GET | `/login/oauth2/code/google` | Служебный callback | `302` |

Профиль содержит только `id`, `email`, `emailVerified`, `createdAt`. Task DTO не содержит owner ID. Токены писем не возвращаются через API. Ограничения частоты применяются к email/auth-запросам и началу Google flow, без перманентной блокировки аккаунта по внешним запросам.

### Состояния интерфейса

Нужны экраны входа с двумя способами, регистрации, ожидания/повторной отправки подтверждения, результата подтверждения, запроса восстановления и нового пароля. Обрабатывать отправку формы, ошибки полей, истечение ссылки, отказ Google, истечение сессии и ограничение частоты. При `401` возвращать к входу; при `403 csrf_invalid` обновлять токен, не повторяя автоматически неидемпотентную операцию. Пароли и токены не сохранять в localStorage; ссылки писем не должны утекать через referrer или стороннюю аналитику.

Область `identity` следует той же структуре, что `tasks`: регистрация и восстановление — сценарии service, хранение — repo. Интеграция Spring Security и Google относится к границе аутентификации; repo не зависит от HTTP-сессии или SecurityContext.

Основание для предлагаемого Google-входа и CSRF-защиты: [Spring Security OAuth2 Login](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/index.html), [настройка Google](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/core.html), [CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html).

## Критерии приёмки

1. Непустая задача добавляется и видна в списке. Пустые строки и строки из пробелов отклоняются сервером.
2. Отметка выполнения меняется в обе стороны и сохраняется после обновления.
3. Удалённая задача исчезает из списка и не возвращается после обновления.
4. После перезапуска backend с той же БД сохранённые задачи доступны.
5. Миграции разворачивают схему на пустой БД; ORM проверяет соответствие схемы, не создаёт её автоматически.
6. Интерфейс корректно показывает загрузку, пустой список и сетевую ошибку, доступен с клавиатуры и удобен на узком экране.
7. README содержит команды запуска и проверки, настройки окружения и описание использования AI.
8. Репозиторий доступен по ссылке; при наличии развёртывания опубликован и URL сайта.
9. Вход через Google и регистрация/вход через подтверждённый email работают; выход завершает сессию, восстановление пароля использует одноразовый токен с ограниченным сроком.
10. Два пользователя не видят и не могут менять задачи друг друга; это проверяется интеграционными тестами, включая запрос с чужим ID.
11. Неверные, повторно использованные и просроченные email-токены отклоняются; конфликт способов входа не приводит к захвату аккаунта. Запросы без сессии или требуемого CSRF-токена отклоняются.
12. Повторная регистрация не меняет пароль существующего пользователя и не раскрывает наличие аккаунта. Неподтверждённый пользователь не получает доступ к задачам.
13. Проверены отказ Google, неверный OAuth state, неподтверждённый Google email и конфликт с локальным аккаунтом; обход проверки ID token невозможен.
14. После сброса пароля старые сессии и токены не работают; после обычного выхода закрывается только текущая сессия. Login/logout не оставляют frontend с прежним CSRF-токеном.
15. Реальные ответы и ошибки соответствуют `openapi.yaml`; спецификация проходит структурную валидацию.

## Границы MVP и открытые решения

Редактирование заголовков, сроки, категории, поиск и пагинация остаются за пределами MVP. Аутентификация добавлена пользователем сверх исходного задания.

Пользовательская модель определена: личные списки после входа. Проектный контракт email использует пароль; изменение на одноразовый код или ссылку потребует пересмотра auth API. Для развёртывания понадобятся Google OAuth credentials, почтовый сервис, домен и HTTPS. Пути frontend `/` и `/login` зарезервированы для OAuth-переходов; остальные пути страниц согласовать с frontend.

Открыты выбор frontend-стека и площадка развёртывания. ORM/мигратор/БД зафиксированы в `AGENTS.md`. Реализацию frontend пока не начинать.

На текущем этапе использован Codex: настройка репозитория, правила коммитов и анализ требований. При реализации дополнять описание фактически выполненной AI работы; не приписывать инструменту ещё не выполненные этапы.


## Backend: реализованный слой хранения

В backend подготовлены JPA entities и интерфейсы репозиториев tasks и identity с единственными Jpa-реализациями через EntityManager. Они обеспечивают insert-only создание, запросы задач по владельцу, блокировку пользователя и атомарное погашение токенов. Email-токены хранятся как SHA-256 hash в lowercase hex; исходные значения не передаются в repo.

Слои http и service пока содержат только описание назначения пакетов. HTTP API, бизнес-сценарии, аутентификация, отправка писем и отзыв сессий остаются следующими этапами. Миграция и публичный API-контракт при изменении структуры сохранены.

Запуск и транзакционные контракты описаны в [backend/README.md](../backend/README.md). Проверки: PostgreSQL через Testcontainers и архитектурные правила ArchUnit.
