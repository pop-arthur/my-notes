# Правила работы над проектом

## Структура и стек backend

- Серверное приложение размещать в `backend/`. Один Spring Boot сервис и одна PostgreSQL БД.
- Язык — Java; веб-слой — Spring Boot / Spring MVC, REST API с JSON.
- ORM — JPA / Hibernate через `EntityManager`. Для каждого репозитория использовать интерфейс `*Repository` и одну реализацию `Jpa*Repository` с `@Repository` и EntityManager. Spring Data repository-интерфейсы не использовать. База данных — PostgreSQL.
- Миграции — Flyway: версионированные SQL-файлы в `backend/src/main/resources/db/migration/`. Применённые миграции не переписывать, изменения оформлять новой миграцией.
- Аутентификация и авторизация — Spring Security. Google — OpenID Connect (Authorization Code flow); email — регистрация и вход с паролем, подтверждение адреса и восстановление доступа.
- Для браузера — серверные сессии и cookie `HttpOnly`, `Secure` в production, `SameSite=Lax`; CSRF-защита обязательна, включая вход и выход.
- Контракт API — `docs/openapi.yaml`. При изменении поведения синхронно обновлять контракт и реализацию.
- Базовые версии backend: Java 21, Spring Boot 4.1.2, PostgreSQL 18, Maven Wrapper 3.9.11. Совместимые версии Spring-зависимостей, Hibernate, Flyway и Testcontainers брать из dependency management Spring Boot; ArchUnit фиксировать отдельно в `backend/pom.xml`.
- Frontend-стек пока не выбран; не вводить его зависимости в backend.

## Коммиты

- Использовать формат Conventional Commits: `<type>[optional scope]: <description>`.
- Допустимые типы: `feat`, `fix`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `perf`, `style`, `revert`.
- `feat` — новая функциональность; `fix` — исправление ошибки; `refactor` — изменение структуры кода без изменения поведения; `docs` — документация; `chore` — обслуживание репозитория и конфигурации.
- Писать описание на английском, в повелительном наклонении, со строчной буквы, без точки в конце. Желательная длина заголовка — до 72 символов.
- Scope необязателен; использовать понятные области, например `api`, `tasks`, `db`, `web`.
- Один коммит должен содержать одно логически завершённое изменение. Не смешивать функциональность с посторонними правками.
- Для несовместимых изменений использовать `!` после типа/scope и пояснение `BREAKING CHANGE:` в теле коммита.
- Примеры: `feat(tasks): add task completion`, `fix(api): reject blank task titles`, `docs: document local setup`, `chore: update gitignore`.
- Не изменять историю уже опубликованных коммитов без прямого запроса пользователя.

## Ценности разработки

### SOLID

- У каждого класса и модуля должна быть понятная ответственность.
- Изменения должны затрагивать минимально необходимое число компонентов.
- Контракты должны быть небольшими и отражать потребности вызывающей стороны.
- Бизнес-правила и сценарии размещать в service; HTTP-преобразования — в http, запросы и детали хранения — в repo. Сервисам разрешено работать с JPA entities.
- Вводить интерфейсы на значимых границах, а не создавать интерфейс для каждого класса.

### Слоистая архитектура

- Организовать код по функциональным областям `tasks` и `identity`; внутри каждой — `http`, `service`, `repo`.
- Направление зависимостей: `http → service → repo` (интерфейсы). Сервисы не зависят от конкретных `Jpa*Repository`. Репозитории не зависят от service/http; сервисы не зависят от HTTP. HTTP не обращается к репозиториям напрямую.
- `http` содержит контроллеры и отдельные request/response DTO. Не возвращать JPA entities из API и не принимать их как HTTP-запросы.
- `service` содержит бизнес-правила, сценарии использования и транзакционные границы составных операций. Сервисы используют JPA entities напрямую; отдельные domain-модели и дополнительный слой портов не вводить; зависеть от интерфейсов репозиториев.
- `repo` содержит интерфейс на сущность и единственную реализацию `Jpa*Repository` с `EntityManager`; модели — в `repo.entity`, ошибки хранения — в `repo.exception`.
- JPA entities имеют защищённый конструктор без аргументов, публичный конструктор создания и getters. Между функциональными областями передавать UUID, без межобластных JPA-связей.
- Создание — insert-only через `persist`/`flush`; не подменять его `merge`. Сохранить именованные ошибки дубликатов, запросы задач по владельцу и атомарное погашение email-токенов.
- `findByIdForUpdate` и `consume` требуют внешнюю writable-транзакцию (`MANDATORY`). Обычные repo-операции участвуют в транзакции сервиса (`REQUIRED`), чтение — `readOnly`.
- Сохранять соразмерность задаче: один сервис и одна база, без микросервисов, универсальных базовых репозиториев и лишних слоёв.

### Контракты service layer

- Сервисы возвращают безопасные типы из `service.result`, а не JPA entities. Эти результаты не зависят от repo; HTTP преобразует их в свои DTO.
- UUID пользователя для task-сценариев передаёт доверенная граница аутентификации, а не HTTP body. Сервисы проверяют существование и подтверждение пользователя.
- Время получать через внедрённый `Clock` / `ServiceTime` в UTC с микросекундной точностью; идентификаторы — через `UuidGenerator`.
- PasswordEncoder: Spring Security Crypto, DelegatingPasswordEncoder с `pbkdf2@SpringSecurity_v5_8`. Пароли не обрезать и не нормализовать; ограничения длины считать по Unicode code points.
- Регистрация и первый Google-вход используют REQUIRES_NEW через TransactionTemplate. Конфликты уникальности обрабатывать только после rollback, не внутри неуспешной транзакции.
- При операциях email-токенов соблюдать порядок блокировок: пользователь → токен. После ожидания блокировки пользователя обновлять его состояние из БД.
- `IdentityMailSender` реализован SMTP-адаптером на JavaMailSender; включение через MAIL_ENABLED (по умолчанию false). Без sender почтовые сценарии явно недоступны до чтения аккаунта; production no-op запрещён. Для разработки используется Mailpit, перехватчики остаются только в тестах.
- Выпуск токена и связанные изменения завершают свою транзакцию до вызова sender. Ошибка доставки не отменяет commit; повторная отправка выпускает новый токен. Надёжная очередь доставки пока не реализована.
- Сброс пароля атомарно увеличивает `auth_version`. HTTP/security-интеграция сверяет версию на каждом аутентифицированном запросе; JDBC-сессии старых версий удаляются после commit сброса.
- `VerifiedGoogleIdentity` — доверенный внутренний ввод после проверки Google ID token Spring Security, не HTTP request DTO. OAuth flow и проверку JWT этим классом не заменять.

### SMTP и публичный origin

- Ссылки писем строить только из APP_PUBLIC_ORIGIN с фиксированными путями /verify-email и /reset-password; не использовать Host/forwarded-заголовки. В production origin — HTTPS без credentials/path/query/fragment; local/test допускают HTTP.
- При включённой production-почте требовать SMTP host, корректный From и пару username/password. STARTTLS (587) — по умолчанию, implicit TLS (465) — альтернатива; none разрешён только в local/test. Проверку сертификата не отключать, mail debug запрещён; connect/read/write timeout — по 5 секунд.
- Письма — UTF-8 multipart text/plain + text/html. Токены URL-кодировать, HTML экранировать; ошибки транспорта не должны раскрывать исходное письмо или credentials.
- Google callback по умолчанию формируется из APP_PUBLIC_ORIGIN. Явный GOOGLE_REDIRECT_URI поддерживается; при одновременной настройке значения должны соответствовать друг другу.
- Секреты SMTP/Google хранить в окружении внешнего backend-хостинга. Cloudflare Worker обслуживает frontend и проксирует API на Spring; credentials не передавать во frontend/Worker. Деплой и создание внешних платных ресурсов — отдельная задача.

### HTTP и сессии

- HTTP реализует контракт `docs/openapi.yaml` версии 0.2.0. PATCH задачи принимает title, completed или оба поля, отклоняет пустой объект и явные null; SQL обновляет только переданные поля атомарно по ID + владельцу.
- Spring MVC DTO отделены от service results; неизвестные JSON-поля, дубликаты полей и scalar coercion запрещены. Секреты в request/response DTO скрыты в toString.
- Сессии — Spring Session JDBC в PostgreSQL, схема V3 применяется только Flyway. Сериализуемая SessionIdentity содержит UUID и auth version; cookie JSESSIONID, HttpOnly, SameSite=Lax, Path=/, Secure по умолчанию. Отключение Secure допустимо только с профилем local/test.
- Вход явно применяет session fixation protection, ротацию CSRF и сохранение SecurityContext. Все POST/PATCH/DELETE требуют CSRF, включая login/register; свежий токен получают через GET /api/auth/csrf.
- Контроллер получает владельца из principal. На каждом аутентифицированном запросе security-фильтр вызывает сервис проверки текущей auth version; repo из HTTP не вызывать.
- Logout закрывает только текущую сессию. Reset публикует service-событие, после commit удаляются только сессии более старых версий. Текущая чужая сессия сохраняется.
- Google OIDC выключен по умолчанию; включение требует credentials и callback URL. Проверку JWT/state/nonce выполняет Spring Security до вызова GoogleIdentityService. После входа хранится только локальная identity, не Google access/refresh/ID tokens. Редиректы фиксированы: / и /login?error=oauth_failed.
- Ошибки контроллеров и фильтров имеют application/problem+json. Отсутствующий sender и отключённый Google дают безопасный 503, не фиктивный успех. Секреты, body и OAuth query-параметры не логировать.
- Лимиты auth-маршрутов применяются по socket IP с bounded Caffeine cache; forwarded-заголовки не доверенные. Приложение рассчитано на один экземпляр и один origin, CORS по умолчанию закрыт.
- /actuator/health публичен и не раскрывает компоненты/детали. API/auth ответы имеют Cache-Control: no-store.

### Production design

- Проектировать понятные состояния интерфейса: загрузка, пустой список, успех и ошибка. Учитывать доступность, клавиатуру и мобильные экраны.
- Валидировать данные на сервере; выдавать согласованные HTTP-статусы и безопасные сообщения об ошибках.
- Все изменения схемы БД выполнять версионированными миграциями. Не использовать автоматическое изменение схемы ORM в production.
- Hibernate должен проверять схему (`ddl-auto=validate`); создание и изменение схемы выполняет Flyway.
- Хранить секреты вне Git; конфигурацию окружений передавать через переменные среды.
- Обеспечить воспроизводимый запуск, health check, полезные логи и инструкцию в README.
- Проверять бизнес-правила unit-тестами, а HTTP, ORM и миграции — интеграционными тестами на совместимой с production БД.
- Для интеграционных проверок использовать PostgreSQL; не подменять её H2. Обязательно проверять изоляцию задач, вход/выход, CSRF и одноразовость токенов подтверждения и сброса.
- Не расширять MVP без необходимости: надёжное выполнение требований важнее количества технологий.

## Ограничения проекта

- Backend реализуется на зафиксированном выше стеке.
- Аутентификация: Google и email + пароль с подтверждением адреса и восстановлением доступа, согласно проектному API-контракту.
- Задачи принадлежат пользователю. Владельца определять из серверной сессии; все операции ограничивать его данными. Не принимать `userId` клиента как основание для доступа.
- Использовать Spring Security для аутентификации. Не хранить открытые пароли, токены восстановления и секреты в логах или Git; не объединять аккаунты автоматически по совпадению email.
- Выбор frontend-стека отложен до отдельного решения пользователя.
- Разбор требований и предлагаемые решения находятся в `docs/task-analysis.md`. Предложения не считать согласованным стеком автоматически.
